# Mula memory and SQLite

## What the Operator remembers

Each account has its own memory store and its own runtime profile. The Operator reads the memory on every turn and saves to it on its own, the way a built-in agent memory would, but Mula owns the storage: every save goes through one pipeline, nothing is ever rewritten, and the owner can see and change all of it on the Memory page.

```text
.runtime/workspaces/<account-id>/memory/
├── store.sqlite3     the append-only store: facts, notes and their versions, audit, last retrieval
├── MEMORY.md         the summary, regenerated by Mula after every change
└── notes/            the notes: a folder of Markdown files you can open in Obsidian as a vault
```

The old Markdown tree (`important-facts/`, `business-knowledge/`, …, `changes.jsonl`) may still be there on an installation that had memory before; it is a legacy copy that nothing reads any more. See "Migrating" below.

A memory is one fact, 3–500 characters, about the **business** or about the **owner**. It carries an id, who saved it (the Operator, you, or the migration), when, and, once corrected or retired, what replaced it and when.

## Notes

Besides one-line facts, the owner keeps notes on the Memory page, in the same format as an Obsidian vault: Markdown with YAML frontmatter, in folders (`suppliers/Aroma Coffee`), linked with `[[Title]]` (also `[[Title|shown text]]`, `[[Title#Heading]]`, `[[folder/Title]]`) and tagged with `#tag` or a frontmatter `tags` list.

- **The vault is the source of truth.** Every `.md` file under `notes/` is a note: its folder is the note's folder and its file name the title. No marker or special field is needed, so a vault written in Obsidian (or by hand) shows up as it is. Folders and files starting with a dot (`.obsidian`, `.trash`, `.git`) and symbolic links are ignored. Empty folders show too.
- **Mula reads it on each visit.** The Memory page's requests scan the folder first; only files whose size or modified time changed are read. A changed file becomes a new version in `store.sqlite3` (saved by "vault"), a file moved with its text unchanged stays the same note, and a deleted file archives its note. The store keeps the history, the index for links, tags and search, and the audit (hashes, never text).
- **Mula writes it too, without replacing anything.** Saving in Mula writes the file exactly as typed (no fields of Mula's are added), through the same sensitive-data filter, line by line. A new note or a rename is refused when a file already sits at that name, and an editor opened before a change (in Mula or in Obsidian) is refused rather than allowed to overwrite it. Archiving moves the file to `notes/.trash/`, as Obsidian does. Mula never deletes a file or removes a folder.
- **Odd files are shown, not hidden.** Frontmatter that isn't valid YAML, or a line that looks like a password or phone number, shows the note with a warning; Mula itself refuses to save such text. Files over 400 KB, files that aren't UTF-8, and a top-level folder called `Facts` (that name belongs to the generated Facts notes) are listed as not shown, with the reason.
- **The same title may be in two folders**, as in Obsidian. `[[Title]]` then means the one nearest the top of the vault (then alphabetical); `[[folder/Title]]` names one.
- **Facts are part of the graph.** The Facts folder holds two generated notes, *About the business* and *About the owner*, so `[[About the business]]` links to the facts, and a `[[link]]` inside a fact counts as a link.
- **Renames don't rewrite links silently.** After a rename the page says how many notes still link to the old title and offers to update them; each updated note gets a new version.
- **Notes are not sent to the Operator.** Its summary and retrieval read facts only, so its prompt is unchanged. Search on the Memory page covers both.
- **Two views.** *Folders* is the tree, the note and its linked mentions, and the editor with `[[` completion. *Map* draws notes as shapes and links as lines, with filters and a local graph. See `src/features/memory/README.md`.

Mula reads the vault when the Memory page asks, not continuously: a change made in Obsidian shows after the page reloads its notes. Obsidian notices Mula's writes by itself.

## Three ways to save

- **The Operator saves on its own.** When you state or confirm something worth keeping, the Operator calls its `remember` tool during the turn. The note under its reply reads `Saved to memory: [12]`. When a fact changed, it saves the new version with a reference to the old one; the old version stays in the history. Turn this off in My agents by disabling the Operator's "Save explicit /remember requests" capability; the tool is then refused and the Operator is told not to claim a save.
- **`/remember` in chat.** `/remember Our coffee supplier is Aroma.` saves a business fact before the turn; `/remember owner | Keep answers short.` saves a fact about you. A repeat is reported, not saved twice.
- **The Memory page.** Add a fact, correct one (the old version moves to History), or retire one (it leaves the summary and retrieval, and stays in the history).

Whoever saves, the pipeline applies the same rules: readable text within the length limits; no credentials, keys, passwords, card numbers, identity numbers, or other people's contact details (your business's own phone and email are fine); and no near-duplicates of a fact already saved. A refusal says why, and is logged with a hash rather than the text.

## What the Operator gets each turn

With the Operator's "Retrieve account memory" capability on, every request carries:

1. the summary (`MEMORY.md`): current facts only, newest first, within the same limits as a built-in memory (2,200 characters about the business, 1,375 about the owner), with `N more in Memory` when there are more;
2. up to three current facts whose words match the request (SQLite FTS5, ranked by bm25, English and Indonesian stop words removed).

Superseded facts never reach a prompt. The **Memory used for the last request** panel shows the matched facts; the summary is always included. The Operator's instructions tell it to cite memory ids and to ask rather than invent when the memory says nothing.

Correcting or retiring a fact changes what future turns get. Earlier replies and the runtime's own conversation history can still contain the old wording; the ids make that traceable.

## One runtime profile per account

The Mula runtime serves one named profile per account under `.runtime/hermes/profiles/mula-<account>/`, each with its own API key, its own runtime sessions and its own secrets file. A request for one account can only reach that account's profile. The runtime's built-in memory (`MEMORY.md`/`USER.md` in the runtime home) stays off in every profile, and the backend refuses to start if a profile turns it on. Profiles are created on signup, and the backend asks the running gateway to serve a new profile right away rather than at its next 30-second rescan, so the first message after signup works. For accounts that existed before, run:

```sh
server/.venv/bin/python server/scripts/provision_profiles.py          # report
server/.venv/bin/python server/scripts/provision_profiles.py --apply  # write, then ./run.sh
```

## Migrating the old Markdown files

```sh
server/.venv/bin/python server/scripts/migrate_memory_entries.py          # report
server/.venv/bin/python server/scripts/migrate_memory_entries.py --apply  # import
```

Each paragraph becomes one entry through the pipeline. Preferences and fun facts become facts about the owner; everything else is about the business; `decisions/superseded.md` is imported and retired at once. The files are left byte-identical. Re-running imports nothing twice.

## Inspect the store

The memory store is the one part of Mula that stays SQLite: accounts, chats and settings are in the PostgreSQL application database (see `server/README.md`, "Database"). Find an account id there, then open its store:

```sh
cd /Users/rafa/Desktop/LARAS
psql "$(grep ^MULA_DATABASE_URL= server/.env.hermes | cut -d= -f2-)" -c "SELECT id, username FROM accounts;"
sqlite3 -readonly ".runtime/workspaces/<account-id>/memory/store.sqlite3"
```

Inside SQLite:

```sql
.headers on
.mode column
SELECT id, target, actor, created_at, superseded_reason, fact FROM entries ORDER BY id DESC;
SELECT id, action, entry_id, actor, occurred_at, detail FROM audit ORDER BY id DESC LIMIT 20;
SELECT entries.id, fact FROM entries_fts JOIN entries ON entries.id = entries_fts.rowid WHERE entries_fts MATCH 'coffee OR supplier';
SELECT note_id, version, folder, title, updated_at FROM note_index ORDER BY folder, title;
SELECT note_id, version, actor, created_at, title FROM note_versions ORDER BY id DESC LIMIT 20;
SELECT note_id, target, alias FROM note_links ORDER BY note_id;
```

Do not write to the store by hand. Deleting or updating a history row (`entries`, `audit`, `notes`, `note_versions`) is refused by the database's own triggers; the `note_*` index tables are rebuilt from the newest version on each save, and `vault_files` (which file each note is, with its size, modified time and hash) is updated by each scan; corrections go through the Memory page or the Operator. If `MULA_DATA_DIR` is set, the workspaces live under that folder instead of `.runtime`.

## Implementation boundaries

The account comes from the signed-in session or from the ticket the backend issued for the turn, never from the client or the model. The store and the summary are owner-only files under `.runtime`, ignored by Git. Append-only is enforced by SQLite triggers, not by convention. The sensitive-data filter is a pattern list; the Operator's instructions and your review on the Memory page are the other two safeguards. Retrieval is lexical: paraphrases can miss, and the summary carries what matters most.
