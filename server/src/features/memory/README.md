# Memory (server)

Each account's long-term memory: an append-only store of facts that Mula owns, a short summary regenerated from it, and the pipeline every save goes through. The Operator remembers on its own with a `remember` tool and gets the memory back on every turn, like a built-in memory would, but the storage, the filtering and the history are Mula's.

## How it is organised

- **Store:** `.runtime/workspaces/<account-id>/memory/store.sqlite3` (owner-only). Table `entries` holds one fact per row: `target` (`business` or `owner`), `fact`, `normalized` (comparison form), `actor` (`operator`, `owner` or `migration`), `created_at`, `origin_message_id` (the reply the Operator was writing when it saved), and `superseded_by` / `superseded_at` / `superseded_reason` (`replaced` or `retired`). An FTS5 index (`entries_fts`) is kept by trigger. Table `audit` records every write; table `retrievals` keeps the last retrieval for the Memory page.
- **Append-only, enforced by triggers:** rows can never be deleted or rewritten, and the `superseded_*` columns can be filled exactly once. A correction is a new row plus a supersession of the old one. The audit table is likewise append-only.
- **Summary:** `MEMORY.md` next to the store is regenerated by `summary.py` after every change and on every read: `About the business` and `About the owner`, current facts only, newest first, as `- [id] fact (date)`, capped at the runtime's own limits (2,200 and 1,375 characters) with `N more in Memory` when cut. The agent never edits it; a hand edit is overwritten on the next request.

## The pipeline (`pipeline.remember`)

Every save, whoever asks, goes through the same steps:

1. **Validate** (`filters.clean`): text only, whitespace collapsed, no control characters, 3–500 characters.
2. **Filter** (`filters.sensitive_reason`): credentials and keys (`api key:`, `password=`, `Bearer …`, `sk-…`, AWS and GitHub tokens, private keys, JWTs), Luhn-valid card numbers and 16-digit identity numbers, and contact details (email or phone) next to a word for another person (customer, employee, family). The business's own details pass. A refusal is audited with a hash and the reason, and the reason is shown to the owner or the model.
3. **Dedupe** (`pipeline.duplicate_of`): an active fact with the same normalized text, or a Jaccard word overlap of 0.8 or more, makes the save a no-op that reports the existing id.
4. **Commit**: insert the row; with `replaces=<id>`, mark that row replaced (same target only, once only).
5. **Audit**: `saved`, `replaced`, `retired`, `duplicate` or `refused`, with ids, hashes and the origin message, never the fact text.
6. **Regenerate** the summary.

Facts that overlap by 0.5 or more without being duplicates are both kept and flagged as `related` on the Memory page, so the owner decides which one holds.

## Who writes

| Caller | Actor | Path |
|---|---|---|
| The Operator, mid-turn | `operator` | `remember` MCP tool in `features/agents/tools.py`, gated by the ticket and the `memory_write` setting |
| `/remember fact` or `/remember owner \| fact` in chat | `owner` | `remember_command` → `owner_remember` before the turn |
| The Memory page | `owner` | `POST /api/memory/entries`, `.../supersede`, `.../retire` |
| `scripts/migrate_memory_entries.py` | `migration` | the old Markdown files, see below |

## What the Operator gets

With `memory_read` on, `retrieve` finds up to three current facts matching the request's keywords (FTS5, bm25, stop words removed in English and Bahasa Indonesia). `context_for` appends to the system prompt: the summary, then the matched facts as JSON, marked as owner-provided reference data. Superseded facts are never sent. When the Operator saved during a turn, the stream ends with a `memory` event and the reply's note reads `Saved to memory: [id]`.

## Endpoints

| Method | Path | Body |
|---|---|---|
| GET | `/api/memory` | — returns `summary`, `entries` (with `related` and history fields), `audit` (last 30), `last_retrieval`, `relative_root` |
| POST | `/api/memory/entries` | `{ target, fact }` → `{ outcome: saved \| duplicate, entry }` |
| POST | `/api/memory/entries/{id}/supersede` | `{ fact }` → the replacement; 409 if already corrected |
| POST | `/api/memory/entries/{id}/retire` | — → the retired entry; 409 if already corrected |
| POST | `/api/memory/search` | `{ question (≤1,000) }` → up to 8 current facts |

## Migrating the old Markdown files

`server/.venv/bin/python server/scripts/migrate_memory_entries.py` reports what it would import; `--apply` imports. Each paragraph becomes one entry through the pipeline (so secrets are refused and repeats are skipped). `preferences/*` and `fun-facts/*` become facts about the owner, everything else about the business; `decisions/superseded.md` is imported and retired at once. The files are left in place and byte-identical, as a legacy copy, and the old `memory_*` tables stay in `accounts.sqlite3`. Re-running is safe.

## Files

`store.py` (schema, triggers, search), `filters.py`, `pipeline.py`, `summary.py`, `service.py` (overview, retrieval, prompt text, `/remember`), `routes.py`, `tests/test_memory.py`. `__init__.py` is intentionally empty. See also `docs/memory-and-sqlite.md`.

## Limits

- Retrieval is keyword-based only. There are no embeddings or semantic search.
- The sensitive-data filter is a pattern list, not a classifier; the Operator's instructions and the owner's review on the Memory page are the other two lines.
- What the Operator chooses to save depends on the model. The summary and the history make its choices visible and reversible.
